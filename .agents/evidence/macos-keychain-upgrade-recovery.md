# macOS CLI 跨构建 Keychain 授权恢复

文档编号：CHECK-135。日期：2026-10-27。状态：原凭据显式授权恢复及新旧程序继续访问通过。
关联：RFC-0008、SPEC-008、TASK-006；原在线实例来自 CHECK-134。

## 固定范围与方法

- Apple Silicon 原生 arm64、macOS 27.0；QQ 7.0.2-53644、NapCat Framework v4.18.41。
- 原程序为 5e9eed4 构建；恢复程序为 432eb47 构建。使用原 main.rs 和生产优化库，无诊断插桩；独立保留原程序，新程序全过程摘要保持不变。使用不同构建的本地 ad-hoc 程序，不使用 Developer ID 证书。
- 新旧程序使用同一原私有状态目录及原在线实例，不导出、复制、删除或替换凭据，不重启 QQ，不要求重新登录 QQ。
- 用户明确授权本次密码/系统授权恢复验证，并确认本轮出现三个 Keychain 提示、均选择“始终允许”。密码只在系统窗口输入，未向 CLI 或聊天提供。
- 原始程序、配置、系统诊断、账号结果及快照只保存在本地忽略目录，公开记录不含本机路径、账号、聊天、凭据、证书标识或设备标识。

## 实测结果

| 步骤 | 观察结果 |
|---|---|
| 授权前 | 新程序 status 返回 CREDENTIAL_UNAVAILABLE；原程序 status 为 ready、online=true |
| 早期尝试 | 一次较短尝试未恢复默认访问，其后多轮等待在300秒超时；用户完成弹窗的确认晚于命令结束，不能据此断言密码授权不可用或必须使用证书 |
| 等待修复 | 显式授权改为遵守 CLI 剩余总时限，最多1800秒；普通来源/权益签名检查仍最多300秒，原作用域、父存活、锁/状态守卫和超时回收保持 |
| 本轮授权 | napcat start --authorize-keychain --timeout 1800 成功退出，整体1732.87秒，处于1800秒时限内；返回 ready、online=true、reused=true |
| 新进程无交互复查 | 新程序 status 成功；随后独立进程各读取5项联系人和最近会话成功，不再需要系统授权 |
| 原程序复查 | 原程序 status 仍成功，实际账号与新程序及原基线相同 |
| 数据与运行保持 | 完整 Registry 与授权前逐项相同：实例、安装、运行、进程和凭据键均未更换；验证程序摘要不变 |
| 诊断 | 新程序 doctor compatibility=supported、canStart=true、api=ready |

这验证了固定组合下“用户完成系统授权 → 后续新程序无交互访问”的实际恢复路径。三项提示分别对应既有签名键和同一运行的两项凭据；CLI不接收用户密码，不另建账号认证系统。当前问题不需要新增证书或更换存储实现。

## 验证与限制

- 授权范围及预算3项、SDK监管7项、公开CLI授权4项测试通过；Clippy全目标、fmt及diff检查通过。SDK原子进程身份/回收测试在允许原进程观察的环境执行；未操作QQ。
- 延长等待只针对用户显式选择的授权流程，不把迟到结果当作成功；成功后仍必须通过默认无交互适配器复查原条目。
- 未证明所有macOS版本、所有未来签名身份、锁定钥匙串/拒绝授权等完整矩阵；不要求用户为此提供Developer ID证书，也不把正式发布签名/公证等同本地运行前置条件。
- 没有执行Windows原生回归、托管CI、线上安装或公开发布；专用QQ在验收结束时保持在线。
