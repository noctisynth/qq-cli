# 自动管理 NapCat 安装与实例

文档编号：RFC-0003。状态：Draft，简化 UX 已确认，底层启动/隔离机制待验证。更新：2026-10-19。
关联：SPEC-001、SPEC-004、PLAN-001、TASK-002、FACT-002、FACT-003。

许可执行策略（2026-10-19，FACT-002）：独立原创CLI与外部API协议实现不等同复制上游代码；自动下载/运行涉及上游复制/使用条款，不能据下载可用推定无限授权。适用范围未知只作提示，不返回LICENSE_UNCONFIRMED、不要求作者证明或确认参数、不参与技术canStart。固定摘要、完整性、精确兼容和归属检查继续生效。捆绑/镜像/修改/商业用途单列发布审计，不因本次实现视为已许可。

## 已确认方向

CHECK-022实现已停止实例的新运行代次内核，公开start/restart接合另验收：使用g1保存旧stopped完整快照、安装、新Plan和原创建根run，并按旧run认领及新run来源索引；复用既有n1记录及其reserved→登记→registered顺序，内部启动键由稳定实例和新run派生，已有消息/启动键保护继续生效。新代次不预设账号或复用旧凭据键，旧资料全部保留。
父生命周期锁先行，Inputs在状态锁内重新核对真实启动输入；状态替换仍要求原停止证明。跨代恢复不得猜测丢失来源/创建记录，已注销登记不能复活；默认指针退役需来源链的签名根身份及目标绑定，避免稳定实例换run后误留旧默认键，也避免仅凭同名实例误删。根身份从已认证的前代来源继承，避免随重启次数无限扫描。
元数据内核10项及完整267项离线回归/检查通过，见CHECK-022；原版Inputs组合、公开停止后start/restart及全部故障矩阵仍未验收，不将内核提升为完整启动结论。

CHECK-020补停止确认并发边界：原生等待后不能仅比较run/安装ID/摘要和阶段，完整实例/安装快照必须保持；确认单独封装，完成证明之后的变化返回STOP_OUTCOME_UNKNOWN，保持登记及原证明，不重发终止。此增量是停止故障矩阵的一部分，不提升真实QQ或完整生命周期结论。
确认落盘故障还覆盖完成证明复用分支；用原创registry文件的只读共享句柄阻止替换，验证错误为unknown、原字节不变，解锁后凭原完成证明恢复，不增加运行时故障注入入口。
unknown详情去掉未经重新核对的state=stopping，只定位原instanceId；避免确认后并发阶段已变时向Agent输出相反状态。

CHECK-021保留原生凭据API的跨进程短锁：独立native::credential_lock边界，最小同步/释放权限、非继承、1000ms等待、线程绑定析构，不充当账号或进程归属能力。架构守卫精准许可该模块及原job两处unsafe，不扩大整个native。临时空文件锁20轮对照后，生产mutex另经原并发6项连续10轮、2项原生异常/释放测试及完整253项回归通过；结论限有界协调缓解有效，底层根因与完整故障矩阵未定。

CHECK-021针对CHECK-020复现的原生凭据恢复读写不一致：进程内串行候选在压力第5轮的原歧义/恢复用例仍报CREDENTIAL_NOT_FOUND，已撤回生产变更；此前串行对照通过不证明修复。继续只用原创临时凭据进行边界/身份及跨进程顺序核对，不改变条目身份/持久化，不新增重试或修补密钥；未验收前不提升完整凭据任务。

注销细节按SPEC-004实施：同生命周期锁下验证原停止完成证明，持久注销意图先于默认活动指针退役与登记删除；只退役精确匹配的默认创建身份，旧签名资料保留。丢登记时凭原注销意图恢复；不把任意缺失ID当作已注销。remove内核5项及原创CLI2项已验证，默认原创建证明缺失时拒绝；完整故障矩阵与真实覆盖仍待完成，见CHECK-020/TASK-002。

公开stop已按SPEC-004接合独立维护模块及响应Schema，原创CLI的选择/并发/重复/缺材料/未知结果验证见CHECK-020；TASK-002从完整生命周期拆出该已验收子项。真实QQ覆盖、完整停止故障矩阵、remove/restart与更新恢复仍未冻结验收结论，不以此推广为运行可靠性保证。

维护机制见CHECK-020：查询能力不升级，显式stop另取最小QUERY|TERMINATE句柄，只作用原签名j1私有Job。Windows文档表明这是不可被进程延期处理的强制终止，故结束共享QQ会话、不能伪称优雅退出或后台例行恢复。停止意图/登记先行，原生返回不等于完整完成；先观察空组并保存完成证明，再更新stopped。Job名称丢失不证明空组，无法核对时保留unknown；后续显式操作重核相同目标，不自动换PID/扫名称。全生命周期共用原startup.lock，停止/重启/注销不能与启动错序。先落地正常停止、预启动取消及持久完成恢复，再完善注销/重启/整体验收，不把单个内核当完整生命周期交付。
status接合采用app/status/pending编排原能力+秘密和受检控制HTTP，不把管理鉴权放入通用消息Backend或普通业务路径。旧无绑定记录保持原未验证状态；已有错误不可静默降级。状态输出新增loginObservation但不填账号，不在持状态锁时等待网络；前后完整实例/安装快照比较防止并发换run。仅OneBot确认身份可以更新ready。
运行后恢复与verify_prepared分离：runtime_store/recovery只核对签名r1/marker及原秘密，允许运行产生的日志缓存；run_job/control只读重开原prelogin能力和t1，绝不重新retain或推断缺失discovery。当前实例/安装完整快照在状态事务内复核；能力固定端点与秘密计划端点一致后才能组合HTTP。两者独立离线验证后再接status，缺记录不自动启动或修复。
受检控制传输实现采用私有transport/owned_wire共用原OneBot的hyper/预算/原socket归属检查，public OneBot入口不变；napcat/control/owned仅将固定Route映射到共享POST，不引入transport到napcat协议的反向依赖。此阶段只用同Job原创HTTP服务，签名运行控制恢复和CLI另行接合。

质量整改完成后恢复登录观察实现：协议模块napcat/control与受检HTTP/运行恢复分阶段。控制仅允许auth/login及QQLogin/CheckLoginStatus；固定状态字段严格布尔，不一致拒绝，未知阶段统一unknown。固定七阶段仅展示，不从阶段推导账号或登记ready。管理鉴权会改变WebUI登录频率状态，但不调用QQ登录/刷新/密码/设备接口。凭据不跨观察持久或重放，失败即返回，不自动重试。

登录观察协议候选见CHECK-016：固定WebUI管理鉴权与QQ身份分离，仅允许auth/login和CheckLoginStatus；2FA/拒绝不重试，不自行签发凭据。控制ready不得提升账号ready，输出仅固定阶段/布尔提示，丢弃二维码URL/原始错误/未知阶段正文。实现应先有纯协议测试，再接原签名预登录归属及同一受检HTTP通道，不向不受信端点发送管理秘密；现已接公开待登录status并离线验收，见CHECK-019；真实原版及完整登录恢复仍未验收。

创建请求查询设计：request get同时覆盖消息写意图和启动创建，不联网、不探测进程、不修改日志或补建签名密钥。创建记录只返回requestId、operation:napcat.start、持久outcome、原instance/run、登记阶段及定向下一步，不把dispatched或登记ready解释为当前在线，不填账号作用域。n1/s1目标不一致、损坏签名或显式--instance冲突拒绝；历史实例缺失/换run仍保留原请求身份。消息与启动共用请求键语义：在同一状态锁内，已被另一类操作占用的键返回REQUEST_CONFLICT；既有双类冲突不猜测选择。无记录/消息查询不访问签名凭据，启动查询只读取原密钥。

默认启动内核及创建请求查询已接合，完整220项离线回归见CHECK-013。下文显式接合时的“零实例另行接合”为历史增量；当前已有受检安装前提下自动创建及请求查询已离线验证，缺安装获取、注销后的默认记录处置和真实完整生命周期仍未完成。查询不把持久dispatched/登记阶段升级为在线，跨消息/创建的请求键在同一状态锁下互斥。

默认启动接合设计：普通start的零实例判定必须在startup操作锁内重读注册表，不能根据锁外空快照直接创建。创建前保存独立d1签名的随机内部请求键（不含账号），中断沿用原键；唯一准备态实例只有与该键n1计划的instance/run一致才恢复，多候选仍要求--instance。唯一待登录实例返回账号为空的检查点，不再次调度；starting/未知只查询，不重放。旧d1对应的registered实例被移除时不自动复活，remove实现须明确处理默认选择记录；缺失/损坏记录不能猜键。精确兼容仍先行（许可只作信息，不作运行阻断），缺安装自动准备和完整登录/注销恢复不因此视为完成。

显式新建接合实施：以独立startup.lock串联--new请求的n1预留、材料准备、s1/j1调度及控制保留，内部短事务仍使用state.lock，固定锁序避免嵌套状态锁。先释放初始预留端口，再准备材料；原生入口重取得固定三端口租约。控制监听固定端点零字节检查仅SERVICE_NOT_READY可在总截止内等待，保留未知或归属冲突不重试/不重启。最多1200次、250ms等待且沿用命令总截止；候选真实兼容门禁仍关闭。零实例默认创建、二维码与运行后完整恢复另行接合，不把显式编排当完整交付。

公开--new已接此编排，生产目录的精确兼容证据仍不满足，不能真实启动；无公开测试绕过。预登录保留成功只返回AUTH_REQUIRED、account:null及带instance的status下一步，不假报ready；已有ready结果仍经严格受管通道和Session核对版本/实际在线身份。未知结果保留请求键并定向查询，不自动重放。原创临时程序集成证据见CHECK-013，非真实原版兼容验收。

端口交接实施项：统一三个本地端口租约，动态预留用于新实例，固定计划复用于调度；固定端口在Job分配前取得，持有穿过原生调度日志，紧接CreateProcess前释放。任一绑定失败必须释放部分租约且不换端口/创建Job；同一状态锁避免本工具并发登记变化，但不承诺原版listen与释放原子或排除特殊SO_REUSE行为。仍以签名固定端点及进程/Job归属作为认证前守卫。

预登录候选固定源码核对见CHECK-015：固定Framework与匹配摘要包先调用WebUI再等待登录，登录后构造OneBot；直接Node监听构造链支持同进程推断，但异步初始化不保证listen完成，QQ实际PID未测。WebUI忙端口可自动递增，CLI仍只检查签名固定端点并拒绝漂移，不扫端口或读日志token。候选未冻结，真实完整兼容证据及启动/端口交接仍待完成。

预登录保留候选（未冻结）：仅成员存在不足以在CLI最后句柄关闭后恢复Job，而登录前API可能尚未监听。拟在创建前签名独立控制端点及预期QQ映像，retain_prelogin对同Job的实际控制服务作零字节归属核对，t1保留成功后写j1.prelogin；旧记录缺控制输入不猜测。已有prelogin只复核原t1/完整进程，不复制修补，后续API必须同完整进程身份，不同则拒绝。原创父子/延迟API对照通过，证明该候选可承接加载器退出；但真实Framework是否登录前开启固定控制端点、控制/API同进程以及QQ继承行为仍缺完整元组证据。公开start尚未接入此候选，不能将原型当作可用启动；若条件不成立，须另行评估保管进程或机制变更，不轮试账号或接管现有进程。

实例创建预留增量：Inputs.reserve_instance在同一状态事务内重核输入，n1签名请求日志先保存随机instance/run、唯一安装快照与无账号Plan，然后登记preparing并保存registered。Fresh持有三个本地监听句柄直到调用者释放，Existing直接返回原登记而不重新抢占运行端口；reserved中断恢复同ID/端口，registered缺实例不复活，损坏日志保留并失败。尚未接公开--new/零实例自动选择，也未证明实际启动端口保留交接或跨进程完整创建竞争，见CHECK-013。

首次发现接合增量：dispatch原生创建前在j1可选discovery中保存已检查QQ映像及登记端点；服务绑定须再匹配该预期。pending status的独立工厂在当前完整实例/安装快照仍匹配时，从签名Job恢复并尝试单次零字节连接（最多2秒且共用截止），验证四元组/进程映像/Job后沿用t1先行和j1绑定。已有绑定只恢复、不再连接/复制；旧日志缺discovery不能推导补建发现输入。普通读取和doctor仍只读。路径仅去掉canonical本地盘符的扩展前缀以匹配Win32映像观测，不归一化UNC/大小写/别名。原创父子链路见CHECK-013，不代表真实QQ子树行为已验收。

已绑定服务登录确认增量：status在starting/login_required可通过j1精确恢复服务及受检HTTP观察登录；缺服务绑定返回SERVICE_NOT_BOUND，status只报告原未验证阶段，不发API。确认事务逐项匹配完整实例/安装快照，版本先行、在线才ready；离线保留login_required。首次发现/绑定与控制面/二维码仍待完成，见CHECK-013。

完整调度绑定增量：dispatch.check_in在现有Transaction内接合Inputs复核、verify_prepared、原版三参数与白名单环境构造，返回私有Checked及Target；input_hash以版本1绑定兼容键、Plan、程序/参数/cwd、过滤环境和各配置SHA-256。launch_in重新完成检查、匹配完整Target后才调用run_job.launch_once；摘要不符不创建Job。公开新建入口尚未接此模块，原版加载的最终文件绑定仍须独立完成，见CHECK-013。

运行材料锁内复核增量：runtime_store.verify_prepared接收已有Transaction，在prepared/starting阶段复核r1认领、运行/安装/端点、整组秘密、独立API凭据和目录/config完整内容，无写入或修复。已用真实start_intent事务及原创计数回调验证不嵌套取锁；不是实际进程启动或运行后恢复，见CHECK-013。

锁内复核增量：Inputs.with_revalidated接收现有Transaction，重新运行完整输入检查并逐项比较安装、QQ路径和兼容键，只有一致才在同一锁的存续期内调用后续操作。原始快照不成为可复用许可；不嵌套获取状态锁，不保证排除外部文件写入。原创锁竞争/变化拒绝证据见CHECK-013，公开新建和最终加载绑定仍待接入。

启动输入检查增量：startup模块将唯一固定版本/摘要安装、产物完整性、最多16个QQ候选、唯一有效安装及精确Framework证据串为失败即停流程。Inputs不序列化且不是启动许可；实际调度前仍须锁内文件复核与进程绑定，不以诊断或本快照绕过。原创正反对照见CHECK-013，真实兼容元组/启动仍未验收。

来源编排增量：acquire按需打开导入文件或固定HTTPS下载，受检缓存不再次访问来源，沿用安装事务及整包验证；固定目录核对先于输入/联网/凭据初始化，许可注记不作前置条件。下载限制已同步SPEC-004、PLAN-001。仅原创本地导入与拒绝路径有离线证据，真实上游下载和完整启动仍未验收；许可解释另见FACT-002，测试修正见CHECK-018。

面向 Agent 的任务操作应尽量自动完成，避免要求创建配置、理解 managed 模式或维护预设账号。
不再公开 profile、managed/external、账号绑定/改绑流程；外部端点接入没有已确认需求，不列为必需交付。
默认管理原版 Framework 环境，保留官方 QQ 窗口，不 fork、不自研加载器。
skill list/get/export 提供任务指引，schema 按需给出详细契约，不把全部内部状态塞进默认结果。

唯一候选实例自动选择，多个候选返回 INSTANCE_AMBIGUOUS，显式 --instance 精确选择。
不能因为多个实例中只有一个 ready 就静默选择，也不按窗口焦点或最近活动决定。
消息引用/游标已带实例和账号时优先按其作用域定位，显式选择冲突即拒绝。
无实例时在已有任务启动授权下有界准备/启动，否则给出明确下一步；诊断和列表不隐式启动。
start 默认复用，无实例则创建，多实例须选择；--new --request-id <key> 明确创建另一实例，同键持久记录防串行重试，跨进程锁防并发重复启动。

未登录 account=null，不预填 QQ 号；登录后从对应实例 API 获取实际身份，status 及业务结果返回简短作用域。
跨调用账号变化返回 ACCOUNT_CHANGED，停止沿用旧消息引用/游标/请求键；Agent status 后按任务授权判断后续。
不提供公开 rebind 或永久 profile 绑定，内部身份代次/运行证据只用于防止旧上下文误操作。
这不能识别未表达的主观登录意图，也不能完全消除检查与执行间上游切号竞态。
身份未知不读取聊天/事件正文或发信；获取实际账号不自动授予业务权限。

## 两类资源与命令

installationId 标识来源/版本/内容已核对的本地安装；instanceId 是稳定实例句柄，重启可复用，内部进程代次另记。
QQ account 是运行时实际身份，不充当安装 ID 或实例 ID。同一安装可被多个实例引用。
已停止实例仍保留配置和安装引用，便于重启；每次运行只选一份完整安装。

- napcat install --version <version>：准备安装，重复相同产物幂等，不启动 QQ。
- napcat install --version <version> --from <archive>：本地导入，校验来源/许可/摘要，不执行脚本或修改原文件。
- napcat installations：列本地已登记安装 ID、版本、必要平台/架构和引用数。
- napcat uninstall <installation-id>：只移除本工具拥有且无引用的安装，被引用返回 INSTALLATION_IN_USE 和实例 ID。
- napcat start [--version <version>] [--new --request-id <key>]：复用或明确创建实例，自动登记；必要时准备已选安装。
- napcat instances：列实例 ID、状态、实际账号和安装 ID，不与安装列表混用。
- napcat stop/restart：作用所选实例，stop 不卸载或删除聊天/发送记录。
- napcat remove <instance-id>：只注销已停止实例、释放安装引用，不清除 QQ 数据或防重记录。
- napcat update --version <version> / rollback：明确切换所选实例的安装，不覆盖其他实例使用的产物。

状态统一 status，登录恢复重复调用有界 napcat start；环境/兼容/能力诊断统一 doctor。
接口整体收敛见 RFC-0004；不增加安装/实例嵌套必经层级；使用 install/uninstall 与 start/stop 的明确动词减少误用及调用 token。
安装卸载不能自动终止使用者，不提供 force 绕过引用检查；需先明确注销停止实例或切换引用。
引用计数、注册表与目录变更必须同步，防卸载/启动竞争，PID/创建时间/所有权核对防误杀。
版本来源元数据可共享，可写配置/日志/凭据/运行目录必须按实例隔离；不能直接共享可写 config。
NapCat 目录隔离不能推定 QQ 数据隔离，真实多实例及同账号冲突仍须验证。

## 版本与兼容性

使用 release/提交/完整包摘要固定安装，启动配套 EXE/DLL/CJS/MJS/原生依赖，不混装。
原版 BAT 选择同目录文件，没有通用版本切换参数；qq-cli 选择对应完整安装完成版本指定。

兼容键包含启动模式、OS/架构、QQ build/安装文件、NapCat 和加载器摘要。
doctor [--version] 为只读证据预检，返回 supported/unsupported/unknown，详细证据按需获取。
未知组合默认不自动首次加载，须另行验证流程及真实实验授权；更新或摘要变化使旧证据失效。
预检区分原生系统架构与CLI进程架构，绑定QQ安装选择及受检exe/major/入口脚本/版本元数据摘要；不以默认版本模板替代实际build。
精确证据按FrameworkStartup/静态/Shell分级，缺失或冲突保持unknown；unsupported是本项目当前机制明确不支持，不推断上游绝无可行路径。
doctor的产物、适用依据、安装元数据、兼容键与实例API分层，canStart为受检前置条件，不是已启动或用户操作授权。
启动实现还须绑定实际加载路径并约束子进程环境，不继承NODE_OPTIONS、NapCat版本元数据路径等覆盖来改变受检对象；不修改用户全局环境。
