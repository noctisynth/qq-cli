# 无 LiteLoader 的桌面会话接入

文档编号：RFC-0001。状态：Draft。更新：2026-10-16。
关联：SPEC-001、SPEC-003、FACT-002。静态核对不构成架构接受或真实运行授权。

## 问题与目标

标准 Shell 初始化自己的会话，无法直接满足保留官方窗口并共享当前会话的要求。
研究不依赖 LiteLoader 的加载途径，优先复用原版 NapCat 产物，减少长期上游维护。
本提案不承诺无注入、不接管已经运行的进程、不创建第二个账号会话作为共享会话替代。

## 候选方案

1. 优先评估原版 Framework 包内 napiLoader.bat、napimain.exe、napiloader.dll 和 nativeLoader.cjs。
2. 原版入口不可用时，记录固定版本的失败点，再论证自有最小加载器；不复制上游业务代码。
3. 仅当有新证据支持时考虑其他进程外接口；当前没有已确认方案。

首选验证方向是方案 1；本轮明确不 fork，尚未冻结加载机制或授权真实运行实验。
真实附件已有原生入口，修正此前必须先自研加载器的假设；NCoreInitFramework 的导出已静态确认。
原生加载器对应目录没有可重建源码，自定义许可的适用授权未确认，都是集成前缺口。
FACT-003 进一步追溯原生文件自 2025-11-09 引入后到本轮 main 观察提交未变；
BAT/CJS 和 Framework TS 仍有更新，不能把原生文件未变扩大为整个项目已停维护。
现有 CI 不验证该 GUI/同会话入口；公开下游报告也没有原版二进制摘要或完整验收，暂无支持矩阵。
Framework 名称不意味着必须使用 LiteLoader；去掉加载依赖不消除 Hook 或注入本身。

## 验收和影响

版本、附件摘要和实际导出已按 DATA-001 静态核对，许可只完成条款审阅，不代表授权已取得。
按 SPEC-003 先澄清授权和原生契约，再做离线契约和明确范围的运行验证。
后续确认目标会话唯一、窗口保留、API 可用、重连与退出、正常输入；不凭初始化返回判定成功。
真实 QQ 测试的运行范围需要与用户既有风险约束一致；未完成前不写已支持。
如失败，记录失败阶段和版本，不将猜测的调用约定继续扩散到产品层。

## 待决项

- 接入机制与此前风险约束的最终边界。
- 原生来源、维护方式、宿主对象契约，以及固定 QQ 版本与原版产物的运行兼容性。
- 快速登录、初始化回调丢失、就绪可观测性、管理 API 隔离和停止 API 不结束 QQ 的可行性。
- CLI 和原生部分的语言、构建方式、命令契约及错误语义。
- 生命周期与升级策略、许可适用性；fork 不在本轮范围，必要变更先记录证据再另议。
