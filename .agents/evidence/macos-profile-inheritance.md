# macOS 同实例 QQ 数据继承与登录恢复

文档编号：CHECK-134。日期：2026-10-26。状态：同实例数据目录继承、保留账号并点击登录恢复通过。
关联：RFC-0008、SPEC-008、TASK-006；此前每次重启重新扫码的基线见 CHECK-133。

## 固定范围与方法

- QQ 官网 DMG 7.0.2-53644、NapCat Framework v4.18.41；固定来源和资产摘要沿用 CHECK-072、FACT-005。
- Apple Silicon 原生 arm64、macOS 27.0；实现提交 5e9eed4。使用原 main.rs 链接该提交的优化库及依赖，保留同一字节的验证程序贯穿首次启动、停止和重启，摘要前后相同。
- 用户授权专用 QQ 的启动、读取、停止和重启；首次扫码后确认完成，重试后的窗口行为明确确认为“保留了账号，但需要点击登录”。仅开放读取权限；未发送消息、操作媒体/事件或接管普通 QQ。
- 原始配置、账号结果、运行快照、日志、程序和上游资产均留本地忽略目录；公开材料只记录脱敏方法、断言与结果。

## 实测结果

| 操作 | 观察结果 |
|---|---|
| 首次启动与登录 | 控制接口 waiting_qrcode；用户扫码后，status 为 ready、online=true，实际账号作用域与登记一致 |
| 首次限定读取 | contact list 和 conversation list 各 limit=5，均成功返回 5 项；就绪 start 返回 reused=true |
| 显式停止 | 原 CLI 返回 stopped，保留实例、安装和 QQ 数据 |
| 中间运行及收尾 | 用户手动退出 QQ 后，status 返回 PROCESS_EXITED，未采纳替代进程；原 CLI 认证 stop 返回 stopped 后，按用户要求再次重启。这是人工退出，不是启动故障 |
| 后继数据与隔离 | 两次后继入口均指向最初 profile-home；成功后继与首次运行实例/安装相同、运行代次不同，profile 设备/inode 一致；凭据键、HTTP/WS 端点均不同 |
| 登录恢复 | 用户确认 QQ 保留账号，需要点击“登录”；无需再次扫码，不是全自动恢复。随后原 CLI 确认 ready、online=true，实际账号与重启前完全相同 |
| 恢复后限定读取 | 再次各读取 5 项联系人和最近会话，成功且实际账号作用域与首次一致 |
| 恢复后复用与诊断 | ready start 返回 reused=true；doctor compatibility=supported、canStart=true、api=ready |

本次成功后继来自已继承 profile 的中间运行，入口仍绑定最初所有者，没有逐代目录复制。真实观察确认目录与账号恢复；引用认证、停止证明及无递归约束由生产 CLI 复核，拒绝路径由下述离线回归覆盖。

## 限制与后续

- 用户后续明确确认中间进程由其手动退出，修正此前原因未定的记录；不再把该观察计为启动故障或待定位缺陷。正常恢复不代表完整故障矩阵已验收。
- 本次证明固定组合下保留账号、点击登录恢复；不承诺免操作登录、跨账号/跨版本数据保全或所有聊天缓存完整。
