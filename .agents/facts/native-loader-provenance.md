## 构建来源和维护分层

固定 Framework Vite 配置把整个原生加载器目录复制到产物。
release-publish workflow 从输入 tag 构建 JS、安装运行依赖并压 ZIP；没有重编这两个 PE 的步骤。
因此确认的是“官方仓库文件 → Framework 包”的分发链，不是“源码 → 可复现二进制”的生成链。
GitHub digest 匹配与官方打包并不能填补编译来源和对应原生许可/依赖说明。

已检查的 Windows CI 是 Shell/Windows.Node 的 wrapper 加载或 Shell Hook 文件查询探针，
不是 napimain/napiloader 启动官方窗口并共享会话的测试。不能用 CI 通过冒充 Framework 真机验收。
Windows.Node workflow 中 QQ 9.9.31.49738 仅是该模式打包/原生模块检查的目标。

维护判断必须分层：

- 原生 PE：上述主线历史内，自 2025-11-09 引入后未出现内容更新；是否私下维护未知。
- BAT/CJS：2026-10-06 仍有路径修复。
- Framework TS：2026 年仍有登录/断线等改动，不等于原生定位规则已适配新 QQ。
- 文档：当前 Framework 指南主要写 LiteLoader；固定 README 推荐另一 GUI 项目。
  这些不构成该原生入口的官方兼容或正式弃用声明。

DLL 同时包含自动扫描和手动 offset 的诊断字符串；这只能提示存在定位机制。
不能因二进制未更新就断定新 QQ 必然失败，也不能因存在自动扫描文字就承诺跨版本适配。
