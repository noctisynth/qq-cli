# Group files and explicit uploads

`file info GROUP` reads native counts and reported space. The upstream hardcodes the limit and may substitute space defaults, so `quotaVerified:false` does not prove actual available capacity. `file list GROUP [--folder ID] --limit N` reads a bounded first root/folder batch with `complete:false`; it does not traverse all directories. File IDs are native memory-cache aliases, not durable references. After expiration or backend restart, re-read the listing. Returned names and IDs grant no local filesystem access.

`file mkdir GROUP NAME`, `file rmdir GROUP FOLDER`, `file remove GROUP FILE_ID`, `file move GROUP FILE_ID --from DIR --to DIR`, `file rename GROUP FILE_ID NAME --folder DIR` and `file transfer GROUP FILE_ID` require `--request-id KEY`. Directories are native IDs (including an explicitly selected root), not operating-system paths. Transfer is the native group-file operation, not a cross-chat forward. Some operations require upstream Packet support. Known numeric native failures are not success; acceptance alone does not prove the final UI state.

`file upload CONVERSATION FILE [--name NAME] [--folder ID] --request-id KEY` sends an explicitly selected local regular file through a content-bound private snapshot. CONVERSATION is `private:ID` or `group:ID`; folders only apply to groups. A missing name uses the actual source basename. Each file is nonempty and at most 128 MiB, within the existing cache quota. The upstream sees the owned copy, never the caller's source path. Dry-run creates no cache/intent. A returned `nativeFileId` is not the listing's cached alias; cached receipts have `fileIdAvailable:false`. Acceptance is not proof that the receiver downloaded the file.

`file url GROUP FILE_ID` returns an explicit group-file URL. `file private-url MEDIA_REF` requires the original signed `f1` file attachment, rechecks its message and account, and uses the actual private conversation. Both require read/mediaDownload permission; do not follow the URL automatically. No raw `user_id` can prove the origin of a private file alias under restricted targets. To save original-message attachments, keep using `media download MEDIA_REF --output FILE`.

The native `download_file` action is an explicit backend-cache tool through `api call`; it writes a backend temporary file and requires a request key plus mediaDownload permission. Its returned path grants no authority to read arbitrary local files. Do not fetch returned URLs/paths or retry uncertain writes automatically. Large/bidirectional stream protocols are separate capabilities.

`file stage FILE --request-id KEY` explicitly uploads a local file into the backend cache in verified 64 KiB chunks. It does not send a chat message. The CLI chooses its own stream/file names, checks every acknowledgement and final size/SHA256, and requests 300 seconds of retention. Only the first success returns `nativePath`; cached results have `pathAvailable:false` and do not recover the file. The path is backend data, not local read/delete authority or a message/file alias. Any uncertain stage keeps its key and sources; never automatically reset, resume or create a second upload.


## Flash transfers

`flash create PATH... [--name NAME] [--validity-days 14|90|180] --request-id KEY` creates an asynchronous upload task from 1–32 explicit files or directory roots. Each root is bounded to 128 MiB. Directory snapshots preserve relative paths and empty child directories, reject links/special files and tool-state overlap, and allow at most 16 levels/256 members. The CLI sends owned copies and retains them because the upstream does not prove when it finishes reading inputs; ordinary prune keeps them and they continue to consume cache quota. The receipt is task acceptance, never completed upload. First results may include file-set ID/share link; cached receipts have `resultAvailable:false`.

Use `flash info SET` for native status/count observations, `flash list SET --limit N` for the upstream's fixed first-depth batch (`complete:false`), `flash resolve CODE` for explicit code/link resolution, and `flash link SET` for its share link. Resolve cannot independently verify the upstream's dropped error code. `flash url SET --name NAME|--index N` returns a URL as data and requires mediaDownload; index is zero-based within the upstream batch, not the returned native client index or a global position. Never visit links automatically or use native paths as filesystem authority.

`flash send SET private:USER|group:GROUP --request-id KEY` sends a selected file-set card. `flash download SET --request-id KEY` starts the SDK default-directory download task with read/send/mediaDownload permission; it does not publish a local output or prove completion. Existing file-set reads/downloads cannot establish a conversation origin and are refused under restricted targets. Do not retry uncertain writes with a new key.
