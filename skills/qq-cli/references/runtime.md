# Maintain the runtime

`preparing`/`prepared` do not prove QQ or an API is running. Resume bounded `napcat start` within authorization; never call planned endpoints or extract credentials. `request get` remains available offline.

Use `napcat installations` for installed artifacts and `napcat instances` for registered running/stopped instances. An installation can serve multiple instances; stopping an instance does not uninstall its package.
Use fixed versions: `napcat install --version VERSION`, then `napcat start` for the selected/default instance. `start` reuses its instance; `start --new --request-id KEY` explicitly creates another. Retain the key on retries so repeated calls do not open duplicate QQ processes.
Starting a stopped instance retains its ID/version with a fresh run and unconfirmed account. Resume preparing/prepared successors using the same instance, never `--new`. Compatibility checks remain mandatory; dispatched/unknown means inspect status, not launch again.
`request get KEY` only inspects creation. `dispatched` is a dispatch return, not verified login. Follow its status action; retain pending/unknown keys and keep creation keys separate from message keys.
Do not predeclare the account. The official window handles QR/password/login challenges; report `AUTH_REQUIRED` and let the authorized user complete a challenge when required. Never claim to have taken over an already running QQ process.
While an instance is `starting` or `login_required`, `status` may include `loginObservation` with a fixed phase and boolean hints. Even `phase: ready` or `coreReady: true` is only management progress: `account: null` and `identityVerified: false` mean no QQ identity has been confirmed. A later status must verify OneBot before using an account scope. Do not derive an account from a QR URL, phase or cached registration. Missing original control material, management authentication failures and second-factor requirements are errors; do not repair secrets, repeatedly retry authentication or bypass ownership checks.
Use `doctor` for a concrete environment, compatibility or connection failure. Unknown QQ/build/loader combinations are not evidence of compatibility; do not bypass a compatibility refusal or substitute Shell/LiteLoader.
An explicitly authorized lifecycle operation on a ready owned instance can record local exact startup evidence only after its original signed dispatch hash, immutable software inputs, original process/Job and online identity are revalidated. `doctor` only reads existing evidence. This does not grant upstream support or compatibility to other versions; do not manufacture a witness or interpret API reachability alone as compatibility. Startup uses an isolated per-run working directory. Unexpected files in a fixed installation still block maintenance and are preserved; do not delete them to pass a check.
When the user explicitly authorizes testing a new exact combination, use `napcat start --version VERSION --new --request-id KEY --verify-compatibility`. This is a bounded startup trial, not prior compatibility evidence. It only permits missing historical evidence; unsupported platforms, negative/conflicting evidence and modified inputs still fail. Keep the original request key and inspect status after uncertainty; do not claim the combination is supported or repeat startup with a fresh key. The flag never applies to automatic starts. Explicit `napcat update --version VERSION --verify-compatibility --timeout 120` can trial the exact installed target under the same checks; without the flag maintenance still requires prior exact evidence. A trial never writes positive compatibility evidence.
`napcat stop`, `restart`, `update` and `rollback` affect the selected session. Execute within the user's authorized maintenance scope, preserving active conversations and unknown write records. Do not terminate another QQ process or displace an account to resolve conflicts.
`napcat restart` checks startup inputs before stopping the selected owned run, then prepares its successor under the same lifecycle lock. It keeps the instance ID and installation version. A pending successor preparation resumes; a dispatched or unknown outcome does not authorize another launch. If the result is uncertain, inspect `status`/`doctor` and use bounded `start` recovery when indicated. Do not automatically repeat `restart`: selecting a completed successor and restarting it is a new maintenance action. Login may require the official window again; only a verified response or status confirms an account.
`napcat update --version VERSION` checks an installed target before stopping the original run and retains the previous installation for rollback. If the target is missing, follow its `napcat.install` action within the authorized task, then repeat the same update. It reuses a selected target version instead of stopping it again. Pending target preparation resumes; unknown dispatch requires status/doctor, not a changed version or another creation key. Account identity must be verified again after a new run. Automatic target acquisition remains unimplemented.
`napcat rollback --timeout 120` uses the authenticated previous installation or the original pending rollback intent. `ROLLBACK_UNAVAILABLE` means there is no signed previous target; do not guess an older version. An unfinished update is not a rollback intent. A rollback preparation resumes the same target rather than switching back again; stopped successors are not revived from stale preparation snapshots. After completion, a new explicit rollback on the newly selected run is a new maintenance action. Follow status/login guidance after an uncertain or login-required result rather than blindly repeating rollback. Each run receives independent credentials; QQ data is outside version transactions.
An update records its signed source, target and action before stop. `VERSION_MAINTENANCE_PENDING` from start/restart means follow the original maintenance action; do not start the source version or replace the intent. Missing original materials fail closed. Explicit removal of the stopped instance retires its active marker while preserving history; it is not routine recovery.
`napcat stop` forcefully ends the selected signed process group, including the shared official QQ window; it is not a logout, graceful exit or draft-save operation. It does not call messaging APIs. Success returns `instanceId`, `state: stopped` and `reused`; `reused: true` means the original completion proof was reused, not a new termination. `STOP_OUTCOME_UNKNOWN` must not be reported as stopped: inspect the same instance with `doctor`, preserve its records and do not choose another PID or repair credentials. Do not use stop as routine recovery for a read/send failure.
`napcat remove INSTANCE_ID` unregisters a stopped instance. `napcat uninstall INSTALLATION_ID` refuses referenced installations; it does not force-stop their instances. No operation should delete QQ private data.
Uninstall also protects signed rollback references and a claimed successor target whose registration has not completed. Preserve an interrupted transition and resume its original plan; do not delete an installation to bypass recovery checks.
Removal requires the original signed stop completion, not just a recorded stopped phase. It preserves credentials, runtime material and old write records. Success returns `state: removed` and `reused`; repeated completion works after the old installation is gone. Missing arbitrary IDs fail rather than being reported as removed. A conflicting global `--instance` is invalid; pass the intended ID once.
